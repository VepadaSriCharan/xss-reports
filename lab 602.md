# Server-Side Request Forgery (SSRF) in Link URL Preview

## Summary

I identified a Server-Side Request Forgery (SSRF) vulnerability in the **LinkSnap** application's **Link URL** preview functionality.

The application allows users to provide a URL, which is then fetched by the server to generate a preview containing information such as the page title, description, and screenshot.

By supplying a Burp Collaborator URL, I was able to confirm that the application's server made an outbound request to the attacker-controlled endpoint.

Further testing with the `file:///etc/passwd` payload demonstrated that the server also allowed access to local files, resulting in the contents of `/etc/passwd` being returned in the application.

## Vulnerable Field

Link URL

## Vulnerable URL

https://kzlabs.in/602.php

## Steps to Reproduce

1. Open the **LinkSnap** application.
2. Navigate to the **Compose** functionality.
3. Locate the **Link URL** field used to generate a URL preview.
4. Enter a Burp Collaborator URL into the **Link URL** field.
5. Click **Generate Preview**.
6. Observe the Burp Collaborator client and confirm that a request is received from the application's server.
7. This confirms that the application server is making server-side requests to a user-supplied URL.
8. Next, enter the following payload into the **Link URL** field:

```text
file:///etc/passwd
```

9. Click **Generate Preview**.
10. Observe that the application processes the supplied `file://` URI.
11. The contents of `/etc/passwd` are returned in the **Raw Response** section of the generated preview.
12. This confirms that the vulnerable functionality can be abused to access local resources from the server.

## Impact

An attacker may be able to abuse the SSRF vulnerability to make requests from the application's server to attacker-controlled or internal resources. Depending on the server's network configuration and the protocols supported by the request handler, this could allow access to internal services, cloud metadata endpoints, local files, and internal APIs that are not directly accessible from the internet.

## Recommendation

- Do not allow users to make arbitrary server-side requests to user-supplied URLs.
- Implement a strict allowlist of permitted domains and protocols for webhook endpoints.
- Allow only https:// and http:// where required and reject dangerous schemes such as file:// and other non-required protocols.
- Consider deploying a Web Application Firewall (WAF), such as Cloudflare WAF, to help detect and block common SSRF attempts.
