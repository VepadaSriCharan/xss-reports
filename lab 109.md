# SQL Injection in Add Menu Item Tags Functionality

## Summary

I identified a SQL Injection vulnerability in the **Burger Palace - Restaurant Dashboard** application.

While reviewing the application, I found an **Add Tags to Menu Item** functionality that allows users to add tags to a menu item. The functionality sends a POST request to the server containing parameters including `res_id`, `menu_id`, `item_id`, and `new_tags[]`.

During testing, I identified that the `res_id` parameter was vulnerable to SQL Injection. Error-based SQL Injection testing caused a server-side error, and further testing with time-based SQL Injection confirmed that the supplied SQL expression was being processed by the backend database.

I then used **sqlmap** to further validate the vulnerability and enumerate the backend database names. The database enumeration was successful, confirming SQL Injection.

## Vulnerable Parameter

res_id

## Vulnerable URL

https://kzlabs.in/109.php

## Steps to Reproduce

1. Open the **Burger Palace - Restaurant Dashboard** application.

2. Navigate through the application and locate the functionality used to **Add Tags to Menu Item**.

3. Select a tag and submit the form.

4. Intercept the request using **Burp Suite**.

5. Observe that the application sends a POST request to:

```text
https://kzlabs.in/109.php
```

6. Identify the `res_id` parameter in the request.

7. Test the `res_id` parameter with SQL Injection payloads.

8. Error-based SQL Injection testing resulted in a server-side `500 Internal Server Error`, indicating that the supplied input was reaching the backend SQL query.

9. Further testing with a time-based SQL Injection payload resulted in a measurable delay in the server response, confirming that the injected SQL expression was being processed by the database.

10. The vulnerability was further validated using **sqlmap**.

11. Sqlmap successfully identified the backend database as **MySQL** and enumerated the available database names.

## Payload Used

### Error-Based SQL Injection

The `res_id` parameter was tested with SQL Injection payloads. The payload `+` resulted in a `500 Internal Server Error`.

### Time-Based SQL Injection

The following time-based SQL Injection payload was used to confirm that the backend database was executing the injected SQL expression:

(select * from (select(sleep(10)))a)

## Impact

An attacker may be able to manipulate SQL queries executed by the application and access or modify database information. Depending on the database privileges and application configuration, this could result in unauthorized access to sensitive data, modification or deletion of database records, disclosure of application information, and potentially further compromise of the application.

## Recommendation

- Use parameterized queries or prepared statements for all database operations.
- Never concatenate user-controlled input directly into SQL queries.
- Apply strict server-side input validation based on the expected data type of each parameter.
- Consider deploying a Web Application Firewall (WAF), such as Cloudflare WAF, to help detect and block common SQL Injection attempts.
