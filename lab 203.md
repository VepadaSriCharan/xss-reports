# Authentication Bypass via Client-Side Manipulation of Mobile OTP Verification Response

## Summary

The application is vulnerable to an authentication/verification bypass due to improper reliance on a client-controlled response value during mobile number verification.

During account registration, the application requires the user to verify their mobile number using a 6-digit OTP. By submitting an invalid OTP and intercepting the server response, it was possible to modify the JSON response by changing the `verify` value from `false` to `true`.

After forwarding the modified response, the application treated the mobile number verification as successful and granted access to the authenticated application without requiring a valid OTP.

## Vulnerable URL

`https://kzlabs.in/203.php?action=verify`

## Vulnerable Parameter

`otp`

## Steps to Reproduce

1. Navigate to the registration/login page:

   `https://kzlabs.in/203.php`

2. Enter a valid name and mobile number.

3. Click on **Send OTP**.

4. The application displays the OTP verification page and requests a 6-digit OTP.

5. Enter an invalid OTP, for example:

   `000000`

6. Intercept the following request using Burp Suite:

   `POST /203.php?action=verify`

7. The request contains the mobile number and submitted OTP:

   ```json
   {
     "phone": "+919876543210",
     "otp": "000000"
   }
   ```

8. The server returns a response indicating that the OTP verification failed:

   ```json
   {
     "verify": false,
     "message": "Incorrect OTP. Please try again."
   }
   ```

9. Intercept the server response and modify the `verify` value from `false` to `true`.

10. Remove the error message from the response.

11. Forward the modified response to the application:

   ```json
   {
     "verify": true
   }
   ```

12. The application accepts the modified response as a successful verification even though an invalid OTP was submitted.

13. The application then grants access to the authenticated account/dashboard.

## Impact

An attacker may be able to bypass the application's authentication mechanism by manipulating the login response before it reaches the client. This could allow unauthorized access to administrative functionality and potentially expose sensitive application data and privileged operations.

## Recommendation

- Perform authentication and authorization entirely on the server side and never rely on client-controlled response values to establish an authenticated session.
- Do not trust client-side values such as `status` to determine whether authentication was successful.
- Create a secure server-side session only after the submitted credentials have been successfully validated.
- Implement a Web Application Firewall (WAF) as an additional defense-in-depth measure to help detect suspicious authentication-related requests.
