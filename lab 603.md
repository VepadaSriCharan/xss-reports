# Server-Side Request Forgery (SSRF) in Service Endpoint Health Check

## Summary

I identified a Server-Side Request Forgery (SSRF) vulnerability in the **PulseOps** application's **Service Endpoint URL** health check functionality.

The application allows users to provide a service endpoint URL, which is then requested by the server to perform a health check.

By supplying a Burp Collaborator URL, I was able to confirm that the application's server made a request to the attacker-controlled endpoint.

Further testing with the `file:///etc/passwd` payload demonstrated that the server also allowed access to local files, resulting in the contents of `/etc/passwd` being returned in the **Result** section of the application.

## Vulnerable Field

Service Endpoint URL

## Vulnerable URL

https://kzlabs.in/603.php

## Steps to Reproduce

1. Open the **PulseOps** application.
2. Navigate to the **Services** section.
3. Locate the **Run Health Check** functionality.
4. Identify the **Service Endpoint URL** field.
5. Enter a Burp Collaborator URL into the **Service Endpoint URL** field.
6. Click **Check Now**.
7. Observe the Burp Collaborator client and confirm that a request is received from the application's server.
8. This confirms that the application server is making server-side requests to a user-supplied URL.
9. Next, enter the following payload into the **Service Endpoint URL** field:

```text
file:///etc/passwd
```

10. Click **Check Now**.
11. Observe that the application processes the supplied `file://` URI.
12. The contents of `/etc/passwd` are returned in the **Result** section of the application.
13. This confirms that the vulnerable functionality can be abused to access local resources from the server.

## Payload Used

### SSRF Confirmation

```text
<Burp Collaborator URL>
```

### Local File Access


## Impact

An attacker may be able to abuse the SSRF vulnerability to make requests from the application's server to attacker-controlled or internal resources. Depending on the server's network configuration and the protocols supported by the request handler, this could allow access to internal services, cloud metadata endpoints, local files, and internal APIs that are not directly accessible from the internet.

## Recommendation

- Do not allow users to make arbitrary server-side requests to user-supplied URLs.
- Implement a strict allowlist of permitted domains and protocols for webhook endpoints.
- Allow only `https://` and `http://` where required and reject dangerous schemes such as `file://` and other non-required protocols.
- Consider deploying a Web Application Firewall (WAF), such as Cloudflare WAF, to help detect and block common SSRF attempts.
