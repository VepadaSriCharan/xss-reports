# Server-Side Request Forgery (SSRF) in Webhook Endpoint URL

## Summary

I identified a Server-Side Request Forgery (SSRF) vulnerability in the application's webhook functionality.

The application provides a **Webhook Endpoint URL** field that allows a user to specify a URL. The application then makes a server-side HTTP request to the supplied URL when the **Send Test Event** functionality is triggered.

To verify the SSRF, I first supplied a **Burp Collaborator** URL in the Webhook Endpoint URL field and received a callback, confirming that the application's server was making requests to a user-controlled URL.

I then tested the functionality using the following payload:

```text
file:///etc/passwd
```

The application processed the `file://` URI and returned the contents of `/etc/passwd` in the response. This demonstrates that the server can be abused to access local files through the vulnerable webhook functionality.

## Vulnerable Field

Webhook Endpoint URL

## Vulnerable URL

https://kzlabs.in/

## Steps to Reproduce

1. Open the application and navigate to the webhook functionality.

2. Locate the **Send Test Event** section.

3. Identify the **Webhook Endpoint URL** field, which accepts a user-supplied URL.

4. Enter a Burp Collaborator URL into the **Webhook Endpoint URL** field.

5. Click the **Send Test Event** button.

6. Observe that a request is received by the Burp Collaborator server, confirming that the application's backend is making a server-side request to the supplied URL.

7. Next, replace the webhook URL with the following payload:

```text
file:///etc/passwd
```

8. Click the **Send Test Event** button again.

9. Observe that the application processes the supplied `file://` URI.

10. The response contains the contents of the `/etc/passwd` file, including system account information.

## Impact

An attacker may be able to abuse the SSRF vulnerability to make requests from the application's server to attacker-controlled or internal resources. Depending on the server's network configuration and the protocols supported by the request handler, this could allow access to internal services, cloud metadata endpoints, local files, and internal APIs that are not directly accessible from the internet.

## Recommendation

- Do not allow users to make arbitrary server-side requests to user-supplied URLs.
- Implement a strict allowlist of permitted domains and protocols for webhook endpoints.
- Allow only `https://` and `http://` where required and reject dangerous schemes such as `file://` and other non-required protocols.
- Consider deploying a Web Application Firewall (WAF), such as Cloudflare WAF, to help detect and block common SSRF attempts.
