# Authentication Bypass via Client-Side Manipulation of OTP Verification Response

## Summary

The application is vulnerable to an authentication/OTP verification bypass due to improper reliance on a client-controlled response value.

During account registration, the application requires the user to verify their email address using a 6-digit OTP. By submitting an invalid OTP and intercepting the server response, it was possible to modify the JSON response by changing the `verify` value from `false` to `true` and removing the error message.

After forwarding the modified response, the application treated the email verification as successful and granted access to the authenticated dashboard without a valid OTP.

## Vulnerable URL

`https://kzlabs.in/202.php?action=verify`

## Vulnerable Parameter

`otp`

## Steps to Reproduce

1. Navigate to the account registration page:

   `https://kzlabs.in/202.php`

2. Create a new account by providing a valid name, email address, password, and password confirmation.

3. After registration, the application redirects to the email verification page and requests a 6-digit OTP.

4. Enter an invalid OTP, for example:

   `000000`

5. Intercept the following request using an intercepting proxy such as Burp Suite:

   `POST /202.php?action=verify`

6. The request contains the email address and OTP:

   ```json
   {
     "email": "kaiju@mail.com",
     "otp": "000000"
   }
   ```

7. The server returns a response indicating that verification failed:

   ```json
   {
     "verify": false,
     "message": "Invalid OTP. Please try again."
   }
   ```

8. Intercept the response and modify the `verify` value from `false` to `true`.

9. Remove the error message from the response.

10. Forward the modified response to the application.

11. The application accepts the modified response as a successful verification and grants access to the dashboard without requiring a valid OTP.

12. The resulting dashboard confirms that the OTP verification was bypassed and the account was treated as verified.

## Impact

An attacker may be able to bypass the application's authentication mechanism by manipulating the login response before it reaches the client. This could allow unauthorized access to administrative functionality and potentially expose sensitive application data and privileged operations.

## Recommendation

- Perform authentication and authorization entirely on the server side and never rely on client-controlled response values to establish an authenticated session.
- Do not trust client-side values such as `status` to determine whether authentication was successful.
- Create a secure server-side session only after the submitted credentials have been successfully validated.
- Implement a Web Application Firewall (WAF) as an additional defense-in-depth measure to help detect suspicious authentication-related requests.
